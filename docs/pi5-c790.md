# Raspberry Pi 5 / C790 live check

The inspected setup uses a Pi 5, C790 on **CAM/DISP1** through a 22-pin
four-lane ribbon, Debian 13 and kernel `6.18.50+rpt-rpi-2712`. Windows duplicates
the gaming monitor (display 2) to the C790 (display 3) at **1920x1080 / 60 Hz**.

Back up `/boot/firmware/config.txt`, change its existing `camera_auto_detect`
to `0`, and add one bridge overlay under `[all]`:

```ini
[all]
camera_auto_detect=0
dtoverlay=tc358743-pi5,4lane=1
```

Reboot after changing this file. The [official overlay mapping](https://github.com/raspberrypi/linux/blob/rpi-6.18.y/arch/arm/boot/dts/overlays/overlay_map.dts)
also maps `tc358743` to the Pi 5 variant. Audio and separate I2S wiring are
unnecessary for this image-only check. Power off before moving the ribbon.

## Restore HDMI after reboot

```bash
cd ~/wow-hardware-fishbot
sudo bash scripts/enablehdmi.sh
```

The script enumerates existing media devices, finds the TC358743 entity,
derives its subdevice and video node, loads the EDID relative to its own
location, and configures the 1080p RGB pipeline. It discards 30 startup frames
and tests ten more with a 15-second stream timeout. Missing devices, absent
signals, other resolutions and command failures stop it. If loading EDID first
activates a new Windows display, enable that display at 1080p60 and rerun.
EDID and media links must be restored after reboot; the script does not
install the boot overlay.

The inspected nodes were `/dev/media0`, `/dev/v4l-subdev2` and `/dev/video0`.
Numbers may change. The Rust capture path currently requires `/dev/video0`;
compare that with the node printed by the script.

Debian 13 rejects the former separate `--fix-edid-checksums` option.
[Current v4l-utils](https://github.com/gjasny/v4l-utils/blob/master/utils/v4l2-ctl/v4l2-ctl-edid.cpp)
repairs checksums by default; both shipped EDID blocks already have valid
checksums.

## Build on ARM64

Run these commands **on the Pi**, not in the Windows shell:

```bash
sudo apt update
sudo apt install -y git curl build-essential pkg-config clang libclang-dev libopencv-dev v4l-utils
```

If Rust is missing, use the [official installer](https://rust-lang.org/tools/install/):

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal
. "$HOME/.cargo/env"
```

Then update the checkout and build. Do not run Cargo with sudo:

```bash
cd ~/wow-hardware-fishbot
git pull --ff-only
cargo build --locked --release --bin capture-test
```

Rustup installs the pinned toolchain. The first OpenCV build can take several
minutes. A Windows executable cannot run on this ARM64 Pi.

## Live test without HID

After building, cast manually in WoW and run while the bobber is visible:

```bash
mkdir -p output
FISHBOT_SWAP_RB=1 timeout 30s ./target/release/capture-test output/pi-live.png output/pi-live-review.png
```

Choose new filenames on later runs. This saves an unmarked PNG and a review
PNG with a green rectangle and prints the template, score and position. It
never opens HID devices. Exit 0 means match, 2 means no match, 1 means error;
the outer timeout returns 124 if capture hangs.

Copy the images from **Windows PowerShell outside SSH**:

```powershell
scp stauffi@192.168.178.107:/home/stauffi/wow-hardware-fishbot/output/pi-live.png "$env:USERPROFILE\Downloads\pi-live.png"
scp stauffi@192.168.178.107:/home/stauffi/wow-hardware-fishbot/output/pi-live-review.png "$env:USERPROFILE\Downloads\pi-live-review.png"
```

On this device raw RGB3 bytes looked correct when decoded as **BGR24**.
Discarding 30 startup frames fixed a partial first image. OpenCV normally
converts RGB3 bytes to BGR, so `FISHBOT_SWAP_RB=1` swaps the decoded channels
back for this device. Its default is `0` for correct RGB3 drivers; only `0`
and `1` are accepted. Test and bot share the capture module and apply this
setting to every frame, including bite monitoring.

The v4l2/FFmpeg path is hardware-confirmed. This new Rust/OpenCV path still
needs the live check: verify colors against the monitor, the rectangle on a
**new cast**, and rejection of a no-bobber frame. The new source image only
checks calibration, not independent accuracy. Larger-bobber bite monitoring
and physical mouse positioning also still need hardware validation.

After this check, the bot needs HID setup and adequate separate power while
USB-C connects to the PC; see [the build guide](building.md). Use the same
`FISHBOT_SWAP_RB` value that produced correct live OpenCV colors.
